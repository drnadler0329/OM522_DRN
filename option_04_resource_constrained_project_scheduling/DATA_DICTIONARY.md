# Project data dictionary

The seven packages contain synthetic operating data generated by the instructor. Option 4 measures
time in working days. All other options measure time in minutes. Distances are in meters for option
5 and in abstract map units for options 3 and 7, where the supplied travel time (in minutes) is what
determines route timing. Weights, priorities, and visit values are priority scores, not monetary
estimates.

Every CSV file has a header row. Identifiers are strings and must be matched by value, never by row
position. An empty cell in an optional column means the value is absent (null). Each instance
directory also contains `schema.json`, which lists every file, column, type (`string`, `integer`, or
`number`), and whether the column may be empty, and `instance.json`, which records the option,
profile, seed, time unit, and the condition the instance is designed to test. The `row_count` in
`schema.json` describes the supplied file only and is not a validity rule. A loader should apply
the declared types even when an optional column is entirely empty. The schema version is 3, recorded as `schema_version` in each
`instance.json` (`schema.json` has no version field).

The following conventions apply to every option:

- A start time is inclusive and a completion time is exclusive, so a resource can begin its next
  task at exactly the time the previous task completes.
- Processing times and activity durations are positive. Travel, setup, and service times are
  nonnegative.
- Travel-time tables are complete and directed, i.e., they contain one row for every ordered pair of
  locations, including a zero row from each location to itself. A missing row is invalid input,
  not zero travel.
- Due dates and due times are soft targets that measure lateness. Time windows, shifts, capacities,
  and availability intervals are hard constraints that a feasible decision must satisfy.
- Coordinates support maps and plots only. The travel-time table determines travel.
- Time windows include both endpoints, so service may start exactly at the window end.
- Each option's `decision.json` uses the top-level keys, field names, and value types of its
  `worked-example/solution.json`, with times at full precision. The instructor's checker reads the
  decision fields listed in the project guide, allows a tolerance of 1e-8 time units, and
  recomputes every other time and every measure.

Input is valid only when it satisfies all of the following rules and every condition that the
option's own section below calls invalid input, and every malformed file used in grading breaks
at least one of them:

- every required file and column is present, every value has its declared type, and every column
  that `schema.json` marks as not nullable is filled;
- each entity identifier is unique in the file that defines the entity (e.g., `job_id` in
  `jobs.csv`), an identifier may appear on many rows of a relationship table (e.g., `precedence.csv`
  or `processing_times.csv`) subject to the option's own rules on repeated pairs, and every
  identifier referenced from another file exists;
- processing times and activity durations are positive, and travel, setup, and service times are
  nonnegative;
- release, arrival, due, shift, availability, window, and day times, and milestone due days, are
  nonnegative;
- capacities, demands, weights, priority weights, visit values, picker speed factors, and
  congestion multipliers are positive;
- every travel-time table contains every ordered pair of locations; and
- every availability interval, shift, and time window starts before it ends.

A condition that neither this list nor the option's section names (e.g., a precedence cycle) never
appears in a graded file.

## Option 4: Scheduling project activities with limited resources

- Times in this option are working days.
- `activities.csv` has `activity_id`, `duration`, `milestone_due` (an optional soft deadline),
  `priority_weight` (penalty per day that a milestone is late), and `locked_start` (optional).
  Locked starts are outside the required scope, and the column is empty in every supplied case and
  in the held-out case, so a loader must accept the empty column.
- `precedence.csv` has rows with `activity_id` and `predecessor_id`. The predecessor must finish
  before the activity starts. The relationships contain no cycle. A relationship may appear on more
  than one row (e.g., `A008,A005` twice in development_small), including in the held-out case, and a
  repeated row adds no requirement.
- `resource_requirements.csv` has `activity_id`, `resource_id`, and `requirement`, i.e., the units
  the activity occupies for its whole duration. It has exactly one row for every activity-resource
  pair (requirement 0 when an activity does not use a resource), and a missing or repeated pair is
  invalid input.
- `resource_capacities.csv` has `resource_id` and `capacity`, the units available at every moment.
- `decision.json` has a `schedule` list with one entry per activity containing `activity_id`,
  `start`, and `completion`.
- The three opening activities have no predecessors but need more crew together than the crew
  capacity, so a schedule that ignores resources is infeasible from the first day.
- The edge case has an activity that needs more crew than exists and is infeasible.
